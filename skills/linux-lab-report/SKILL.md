# 编写 Linux 实验报告

## 这套报告要解决什么问题

学生是大二上学期，刚学完 Windows 的基本操作，第一次面对纯命令行。他们的困难不是「命令记不住」，而是**没有心理模型**：不知道自己在哪、不知道敲下去会发生什么、不知道错了怎么回头。所以这份报告不是命令手册，是**一份手把手的陪练脚本**。

理解了这一点，下面所有格式约定就都有了理由——它们都是为了让一个紧张的新手能独自走完全程，而不是在第二步就卡住然后放弃。

## 三条设计主线

### 1. 一切挂到 Windows 上

学生已经会的东西是唯一的锚点。每一个新概念都要挂上去：

> `pwd` → 「等于资源管理器顶部的地址栏」

这不是给「提示」凑字数——它让学生的脑子从「我在学一个陌生系统」变成「我在换一种方式做同一件事」，后者学习负担低一个数量级。**每一条新命令都必须有一句 Windows 对照**，用 `win()` 写。真的没有对应物的（比如 `df -i`、`ln`），就直说「没有对应物」——这本身也是有效信息，学生对「这是 Linux 独有的机制」会印象深刻。

### 2. 每一步都要能自己判断对错

新手最大的焦虑是「我敲了，但不知道对不对」。所以每一组命令后面必须紧跟一条 `ok()`：

> 【正确】`pwd` 应显示 `/root/project`；`ls` 应看到 `code`、`doc`、`build`、`script` 四个目录。

关键是**给出可核对的具体值**，而不是「应该没问题」。第一条命令就要给这个待遇，因为对错自检是学生继续往下走的信心来源。

### 3. 把坑提前讲掉

`warn()` 用来写「按常理会踩、但踩了会卡很久」的坑，且必须写清**踩了怎么办**：

> 【注意】如果报错 `File exists`：说明你已经建过了，不用重来，直接 `ls` 看一眼继续。

一个班几十号人，同一句话讲一次写在纸上，比课后被问二十遍省事。反过来，不要把所有边界情况都塞进去——只写「新手一定会遇到」的。

## 风格约定

### 命名：短、无下划线

命令里的文件名要**短**，且**不用下划线连接**。这是硬约束，理由很实在：新手在终端里打长单词会打错，而 `_` 在键盘上要按 Shift，是出错高发区。

- 好：`main.c`、`note.txt`、`run.sh`、`app.c`
- 差：`software_project`、`main_build.c`、`setup_guide.txt`

目录名同理：用 `code doc build script`，不用 `source_code documentation`。

这条规则会连带影响实验设计。如果某个实验必须用长名字，说明这个实验的粒度可能太大，考虑拆开。

### 站点：动词 + 冒号 + 一句大白话

站点头用「（N）动词：大白话」的形式，让人一眼知道要干什么：

- `（1）看家：我在哪？这里有什么？`
- `（2）建房：把项目目录结构搭起来`
- `（3）造物：建文件、往里面写内容`
- `（4）搬运：复制、重命名、删除`
- `（5）清理现场`

不要写「文件与目录的基本操作」这种教科书式标题——学生看到第一反应是「这要背多少东西」。用动词起头，配合一个日常比喻，学生的预期就变成「我要做一个具体的事」。

编号用**手写的中文括号**（`（1）`），不用 Word 自动编号。原因是章节会增删移动，自动编号容易乱，而且老师会手动调顺序。

### 一个站点的固定骨架

每个站点严格按这个顺序，不要漏项也不要调换：

```
（N）站点标题
  1. 编号任务（一句大白话说这一步做什么）
     • 命令（绿色）          ← cmd()
     【正确】…               ← ok()，至少一条
     【提示】Windows 对照：…  ← win()
     【注意】…               ← warn()，有坑才写
     截图要求：…             ← shot()
     【截图占位符】           ← 自动生成
     （空行）
  2. 下一个编号任务 …
```

「截图要求 → 占位符」要写在**每个任务**后面，不要攒到站点末尾。这样截图本身就是逐条自检，学生交上来的报告也能一一对应。截图要求要写清「画面里必须能看到什么」，否则学生会截一张什么都看不出来的图：

> 好：截取 `ls` 的输出，能看到 `main.c`。
> 差：截取 `ls` 命令的截图。

### 颜色与字体

颜色是**语义**，不是装饰——学生看颜色就知道这条信息的性质，比读文字快。

| 用途 | 颜色 | 形式 |
|---|---|---|
| 正文 | `000000` | Consolas + 仿宋，sz 21（10.5pt） |
| 命令 | `00B050` 绿 | 行内，与说明文字同段 |
| 【正确】【提示】 | `0070C0` 蓝 | 左缩进 420 |
| 【注意】【错误】 | `C00000` 红 | 左缩进 420 |
| 截图要求 | `808080` 灰 | 斜体，左缩进 420 |
| 【截图占位符】 | `92D050` 浅绿 | 居中斜体 |
| 一/二/三/四 标题 | `000000` | 华文中宋加粗 |
| 站点标题 | `000000` | 华文中宋加粗 |
| 表格表头 | — | 仿宋加粗，底纹 `E2EFDA` |

**不要用 emoji**。用 `【提示】`、`【注意】`、`【正确】`、`【错误】` 这些中文方括号标签——在 Word 里排版稳定，打印出来也清楚，而且和整个文档的字体风格一致。

### 三张前置/后置表格

每份报告都带这几张表，它们是全篇最常被回看的部分：

1. **【开工前：Windows → Linux 速查卡】**（正文开头）——3 列：你熟悉的（Windows）/ 对应的（Linux）/ 关键差异。只放**本讲真正用得到**的 4~6 行，不要把所有差异都堆上来。
2. **【本次实验常用命令】**（速查卡之后）——3 列：命令 / Windows 里对应什么 / 作用。这份报告里用到的每条命令都要在这里出现。
3. **附：本次实验常见报错速查**（正文末尾）——3 列：报错提示 / 真实含义 / 怎么办。放 4~6 条真实会遇到的报错。

三张表都用灰色细边框（`808080`，sz 4），表头行底纹 `E2EFDA`。

### 难度递进

站点顺序按认知负担递增：**先看清楚 → 再动手建 → 再改动 → 最后删除**。删东西放最后，因为那是新手最怕的操作，等他们建立信心之后再讲。

「清理现场」永远是最后一个站点——养成保持服务器干净的习惯，也顺便复习删除操作。

### 实验体会要问得具体

不要写「谈谈你的收获」这种题，学生只会抄一段废话。问**需要回想具体操作**的问题：

> 本次实验中你最容易敲错的是哪条命令？为什么？
> 回想一下，这些操作在 Windows 里你是怎么完成的？哪个更快？为什么服务器上要用命令？

第二类问题特别有价值——它逼学生把这一节学的东西再挂回 Windows 锚点上，正好检验第 1 条主线有没有生效。

## 运行环境

生成和打分都依赖 `python-docx`（Python 3.8+）：

```bash
pip install python-docx
```

（skill 目录下有一份 `requirements.txt` 写着同一个依赖，用 `pip install -r <skill 目录>/requirements.txt` 也行。）

**这是拿到这个 skill 后第一个会撞上的问题**——`scripts/labdocx.py`、`scripts/dump.py`、`evals/grade.py` 都 `import docx`，没装就直接 `ModuleNotFoundError`。动手写报告之前先确认一句：

```bash
python -c "import docx; print(docx.__version__)"
```

报错就先装。若 `python` 不可用，试 `python3`；Windows 上也可能是 `py -3`。

## 怎么生成

用 `scripts/labdocx.py`。它在 `assets/template.docx`（从现行实验报告抽出的空白模板）上做原位改写，**外壳表格、页眉、样式表、编号定义全部原样保留**。

写一份 spec 文件（Python），然后：

```bash
python scripts/labdocx.py spec.py "输出路径/2512XXXX_某某某_实验报告_N_标题.docx"
```

脚本在生成前会自己跑两道检查，不通过就直接报错、不产出文档：

- **`check_marks()`** —— spec 里混进了 `**`、`##`、反引号。这些是写 Python 字符串时手
  滑敲出来的 markdown，不会被解析，只会原样打进 Word 变成正文里的星号。报错信息会
  指出是哪个字段的哪一条，照着删掉即可。
- **`verify_template()`** —— `TPL_INDEX` 和当前模板对不上了。**改过模板就会这样**：
  加一段、删一行，后面所有段落编号整体错位，而错位的后果是静默的（不报错、文档能开，
  只是占位站没删掉、站点标题整批丢失）。报错会列出对不上的地标，这时去跑
  `dump.py` 重新核 `references/skeleton.md` 那张表。

这两道检查都来自实际踩过的坑，不是防御性编程。

spec 是一个叫 `SPEC` 的字典，字段：

| 字段 | 说明 |
|---|---|
| `title` | 项目名，如 `目录与文件基本操作`（自动拼成 `Linux目录与文件基本操作`） |
| `num` | 实验序号，整数 |
| `goals` | 实验目的，字符串列表（3~5 条，动词开头） |
| `env` | 实验设备及环境，字符串列表 |
| `intro` | 实验步骤引言，一段话 |
| `card_header` | 速查卡标题（省略则用模板默认） |
| `card` | 速查卡数据行，`[(Windows, Linux, 差异), ...]` |
| `cmd_header` | 常用命令表标题 |
| `cmdlist` | 命令表数据行，`[(命令, Windows对应, 作用), ...]` |
| `sites` | 站点列表，`[{'name': ..., 'tasks': [{'text': ..., 'body': [...]}]}, ...]` |
| `errors` | 报错表数据行，`[(报错, 含义, 怎么办), ...]` |
| `questions` | 实验体会问题，字符串列表 |

`goals` / `env` / `questions` 的条数**不受模板槽位限制**：模板里分别是 3 / 6 / 2 个
槽位，写多写少都由 `siblings_from()` 自动伸缩。但正因为会自动伸缩，写完务必按
上一节第 1 条搜一遍占位文字——伸缩逻辑出问题时，症状就是槽位没清干净。

站点的 `body` 用 `scripts/labdocx.py` 里的积木函数拼：

```python
from labdocx import cmd, ok, win, tip, warn, wrong, shot, gap

SPEC = {
    'title': '链接与磁盘空间管理', 'num': 5,
    'goals': ['理解硬链接与软链接的区别…', '…'],
    'env': ['云平台：阿里云ECS云服务器', '操作系统：Rocky Linux 8.10 64位'],
    'intro': '本次实验要弄明白：同一个文件为什么可以有两个名字。',
    'card': [('快捷方式', '软链接（ln -s）', '删掉原文件，快捷方式就失效')],
    'cmdlist': [('ln', '没有对应物', '创建硬链接')],
    'sites': [
        {'name': '（1）分身：软链接与硬链接', 'tasks': [
            {'text': '给 note.txt 建一个硬链接。', 'body': [
                cmd('ln note.txt note2.txt', '创建硬链接'),
                ok('ls -i 看到的两个 inode 号完全一样，说明它们就是同一个文件。'),
                win('等于给同一个文件起了第二个名字，不是复制。'),
                warn('删掉其中一个，另一个还在——这就是硬链接和复制的区别。'),
                shot('截取 ls -i 的输出，能看到两行 inode 号相同。'),
                gap(),
            ]},
        ]},
    ],
    'errors': [('No such file or directory', '路径错了，或文件不在这里', '先 pwd 看位置，再 ls 看有什么')],
    'questions': ['硬链接和软链接的区别，你能用一句自己的话说清楚吗？', '…'],
}
```

积木函数一览：

| 函数 | 产出 |
|---|---|
| `cmd(命令, 说明)` | `输入 <绿色命令> —— 说明` |
| `ok(文本)` | 【正确】（蓝） |
| `win(文本)` | 【提示】Windows 对照：（蓝） |
| `tip(文本)` | 【提示】（蓝，不带 Windows 对照） |
| `warn(文本)` | 【注意】（红） |
| `wrong(文本)` | 【错误】（红） |
| `shot(文本)` | 截图要求（灰斜体，自动加前缀） |
| `gap()` | 空行 |

`【截图占位符】` 由脚本自动加在每个 `shot()` 之后。

## 写完之后一定要验证

生成完不能直接交。至少检查三件事：

1. **有没有残留的模板占位文字**。这是最容易漏、后果最直接的一类错误：模板里
   实验目的有 3 个槽位、设备 6 个、体会 2 个，内容比槽位少时，多余槽位会带着
   「【此处填写实验目的第 3 条：一句一个能力点，动词开头】」原样留在文档里交到
   学生手上。**数站点、数表格是查不出这个的**——结构全对，文档里就是多着一行
   占位提示。生成后直接在全文里搜 `【此处填写` 和 `【问题`，搜到就是没清干净。
   （`scripts/labdocx.py` 的 `siblings_from()` 已经按块签名收边并清空多余槽位，
   但如果你改了模板或手写了段落块，这个检查仍然要做。）

2. **结构**——用 `scripts/dump.py` 把生成的 docx 结构导出来看：站点编号是否连续、
   表格行数对不对、每种元素是不是都还在（尤其别把某个站点整段漏掉）。顺便确认
   列表块没有溢出：实验目的的多条应该都带同一个 `num=5`，设备都带 `num=6`，
   体会问题都带 `left=420`。如果某条的 `pPr` 变了样，说明它吃到了块外的段落。

3. **字体和颜色**——确认标题是华文中宋加粗、命令是绿色、注意是红色。改过段落文字的段落最容易掉格式，因为多 run 段落的第一个 run 不一定是主格式所在的 run。

4. **正文里没有混进 markdown 记号**。spec 是写成 Python 字符串的，写的时候手会习惯性敲
   `**加粗**`、`` `代码` ``、`## 标题`——但这些记号不会被解析，会原样打进 Word 里，
   变成正文中间突兀的星号或井号。同样地，`\n` 在普通字符串里是换行符、在命令示例里
   又常想表达「这里要换行」，容易两边都写不对。搜一遍 `**`、`##`、反引号，有就删掉。
   （模板抬头那行本身就带 `25**` / `***` / `2512****`，是学号占位，别误删。）

   这一条值得单独列出来，是因为它**不会报错、也看不出来**：文档能正常打开，颜色编号
   全对，只有把正文读一遍才会发现星号。我在三份报告里都犯过同一个错，所以别靠记性。

如果本地有 Word，可以导出 PDF 再渲染成图片肉眼看一遍——颜色和编号这类问题，看一眼比读 XML 快得多。但注意**肉眼看 PDF 查不出第 1 类和第 4 类错误**：占位文字和星号都长得跟正文一样顺眼，一眼扫过去根本不会停。这两条必须用搜索来做。

上面这四条 `evals/grade.py` 已经全部自动化了，写完直接跑一遍比人眼可靠：

```bash
python evals/grade.py "输出路径/2512XXXX_某某某_实验报告_N_标题.docx"
```

19 条逐项 PASS/FAIL 带证据。哪条红了就照证据修，改完重跑。用法见 `evals/README.md`。

## 参考文档

- `references/style-spec.md` —— 完整的样式规格（每个元素的确切 XML 属性、编号定义、表格边框），要改模板或排查格式问题时读它。
- `references/skeleton.md` —— 模板 docx 的段落编号蓝图，说明每个编号对应哪个元素。改 `scripts/labdocx.py` 里的 `TPL_INDEX` 时读它。

## 不要做的事

- 不要新建 docx 再往里塞内容。外壳表格和样式表是这个模板的根本，重建必丢东西。永远在 `assets/template.docx` 上改。
- 不要在报告里用 emoji。
- 不要用长文件名或带下划线的文件名。
- 不要把命令写成孤立的一行——每条命令都要有说明、有 Windows 对照、有预期结果。
- 不要写「谈谈你的收获」这类空的体会题。
